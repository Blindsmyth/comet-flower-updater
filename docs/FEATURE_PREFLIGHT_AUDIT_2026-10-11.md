# Firmware rewrite: feature evidence and gates

This audit records what the project can claim before another pedal test or a broader firmware rewrite. “Static” means source, image bytes, disassembly or offline tool behavior. “Pedal” means an owner observation of the exact version tested. Later files do not inherit a prior build's pedal result merely because they share a name.

## Exact-image findings from this audit

- `Controller TEST Updater.exe`: firmware resource 0x81 SHA-256 `c6317cacfc28b0f49bed679b73fe1da6632b2cda4dd77523beb5a24b6d812f59`; FS resource 0x88 equals `fs_cf_ab.bin` (38 files). It does **not** contain MUFFT.
- `Updater + MuffT.exe`: firmware resource 0x81 equals `res1_cfupd.bin`; FS resource 0x88 equals `fs_cf_ab_mufft.bin` (39 files). It does **not** contain the controller.
- Both updater images contain an older MUFFX than today's `build/MUFFX.ZD2`. Size is unchanged; differing bytes are offsets 0x8–0xb (CRC) and 0x2ee–0x2ef (`dspload`). This is an artifact/version fact, not a claim of new DSP code.
- The current controller updater's six flash stages passed `check_updater_stages.py`; `validate_controller_fw` passed; a source rebuild was byte-identical. These checks did not execute either updater or touch the pedal.

## Evidence rule for the rewrite

For each change, keep a short record with: **claim → exact stock instructions/data → dependency slice and task context → source change → exact binary diff/resource hash → offline failure checks → owner observation**. Promote a claim to “known on pedal” only for the exact artifact and behavior observed. A disproven assumption returns to the design stage; a new build gets its own identity and gates.

Order the rewrite around recoverability: preserve the stock res5 update path, version-pin stock inputs, isolate one main-firmware feature at a time, verify its binary diff and flash stages, then measure its behavior. The existing custom effects and branding are successful proof of the patching method, but they are not evidence that every untraced path in a replacement firmware is safe.

## Timing calibration needed before a CPU-based save gate

`effects/common/mp_timing.h` stores `TSCL` differences between successive effect callback entries. It does not directly sample a hardware audio interrupt timestamp or an independent wall-clock timer. The observed ~50.6k count would correspond to ~139.5 MHz **only if** TSCL advances continuously between 16-frame callbacks; the boot PLL interpretation yields a different nominal clock and the physical reference oscillator has not been measured. Stock firmware includes a CPU `IDLE` instruction and BIOS idle/task hooks, so idle behavior must be checked rather than assumed to be absent. [TI's C674x CPU guide](https://www.ti.com/lit/ug/sprufe8b/sprufe8b.pdf) defines TSCL as a CPU clock counter; the [C6745/C6747 technical reference](https://www.ti.com/lit/ug/spruh91d/spruh91d.pdf) describes CPU clock gating in idle. Those facts alone do not establish which clock state occurred during the recording.

To resolve this, record a TSCL delta and a separate running hardware timer delta over the **same known number of audio callbacks**, and read the PLL/control state in that build. Verify callback cadence and sample rate independently. Compare the count while the unit is otherwise idle and while background work is active, then measure a populated five-slot patch. Until the relationship is established, the decoder reports a conditional clock equivalent and CF Loader must not convert Probe 10's freeze setting into measured cycles or approve saving from it.
