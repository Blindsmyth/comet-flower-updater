### S3.F1 - The audio Swi's effect stack (0x11816140) sits inside the shared
### L2 Hwi/Swi stack region, not a separate per-effect allocation (likely,
### synthesis of two already-confirmed facts)
recon/14 (section "CONFIRMED ON THE PEDAL (2026-10-06, CF MEMPRB...)") reports
the CF MEMPRB probe, running as a slot effect's own process callback, read its
own `B15` as `0x11816140` (L2 RAM) - this is the stack pointer value visible
*inside* a per-slot effect kernel, i.e. the stack an effect actually runs on.

Independently, recon/16_audio_hw.md section C7 and docs/helpers/STACK_AUDIT_
2026-10-13.md ("Interrupt-stack reservation confirmed") establish, from
`c0163e94..3eb4` (`MVK 0x3468,B5; MVK 0x3000,B4; ADD B5,B4,B4; STW B4,*A3[6]`),
that the firmware reserves a single 0x3000-byte (12,288 B) L2 region
`0x118134a8..0x11816468` as the system interrupt/Swi stack (top = highest
address = `0x11816468`), and that `c015ec80`/`c016d600` switch B15 onto this
region's top on Hwi/Swi entry (not a per-task stack).

`0x11816140` lies strictly inside that reservation
(`0x118134a8 < 0x11816140 < 0x11816468`), 0x328 (808) bytes below the
reservation's top. Since the audio Swi (`11818ba0`, priority 15, confirmed in
recon/16 C3) is dispatched through exactly this same Hwi/Swi-entry stack-
switch path, and the per-slot effect callback is called directly from inside
`11818ba0`'s slot loop (`11818c0c LDW *+B11[B10],B5; 11818c16 BNOP B5,0`,
chunk_19/recon/map/chunk_19.md row `11818ba0`) with no further stack switch in
between, the simplest account that fits both facts is: **effects run on the
shared 12 KiB Hwi/Swi stack, not a dedicated per-effect or per-slot stack**,
and by the time control reaches the slot callback roughly 808 bytes of that
12 KiB are already spent by the Hwi entry + Swi dispatch + the Swi's own
pre-loop local variables.
Confidence: **likely** (the two source facts are each confirmed on their own;
the connection between them - that the probe's B15 and the C7/STACK_AUDIT
reservation are the *same* stack - was not re-derived from fresh disassembly
this session, it is an evidence-consistent inference). Not re-verified: a
second on-pedal probe placed in a *different* slot index to confirm the 808-
byte figure is stable rather than coincidental to slot 2 (pedal slot) in the
one MEMPRB run on record.
Commit: this finding.

### S3.F4 - What is adjacent to the stack's low end: the audio slot-callback
### table and the hardware peripheral-pointer block (confirmed addresses;
### likely as an overflow consequence)
recon/16_audio_hw.md section C7 (L2 occupancy table) places, in increasing
address order and by its own confirmed evidence:
- `0x1180bd40..0x118134a8` (7761 B): "cinit RLE-initialized data, **including
  callback tables and peripheral pointers**"
- `0x118134a8..0x118164a8` (0x3000 = 12,288 B): the interrupt/Swi stack
  reservation (S3.F1 above), **immediately above** the first range.

recon/16 section "F1. Peripheral base pointers live in cinit-initialised L2
data" decodes exactly what lives in that first range, by address:
`0x1181329c`=McASP0 cfg base, `0x11813314`=McASP1 cfg base,
`0x1181340c`=I2C0 base, `0x11813414`=codec I2C address,
`0x11813418`=I2C bus rate, `0x11813450/54/58/94`=EDMA3 CC0+shadow bases,
`0x11813468`=SYSCFG, `0x1181346c`=PSC0, `0x11813470`=PSC1,
`0x11812fec`=SPI0, `0x118133bc`=sample rate (44100), `0x118133b0`=19.2 MHz
MCLK, `0x118133c4`=TIMER64P0. All of these sit **below** `0x118134a8`, i.e.
on the low (overflow) side of the stack.

Also in that same range, confirmed independently in recon/map/chunk_19.md's
"Data" section and reused throughout recon/16/17/18/20: **`0x118133e0..
0x118133f0` is the live 5-slot effect-callback table** (one function pointer
per slot, read every iteration of the audio Swi's slot loop at `11818c0c`),
and **`0x11813490`** is the second per-slot config/dispatch table read by
`cfg_slot_dispatch` (`c014f594`). Both tables are between `0x118133e0` and
`0x118134a8`, i.e. the *closest* data to the stack's low boundary - closer
than the peripheral pointers above.

So a stack overflow (B15 decrementing below `0x118134a8`) would first
overwrite the **slot-callback table that the audio Swi itself is actively
reading** (`118133e0`) and the second per-slot table (`11813490`), and then
the McASP/I2C/EDMA/SPI/sample-rate/clock peripheral-pointer block
(`0x1181329c..0x118134a4`). Corrupting the slot-callback table would make the
Swi call garbage addresses for one or more slots on the very next audio
block; corrupting the peripheral pointers would not take effect until code
re-reads them (most are read once at init, per recon/16 F1/C1, so a stale copy
might not immediately crash the running audio path, but any re-init or the
codec-mute/unmute path - `c013dca0` etc., recon/16 section 1 - would then
write through a corrupted I2C/codec address).
Confidence: **confirmed** for every address and its labelled content (all
three source rows cited above); **likely** for the causal claim ("overflow
corrupts these first") - this is argued from address adjacency and the known
direction of growth (SP decrements on this C6000 target, per every push
instruction cited in STACK_AUDIT/STACK_CONTEXT, e.g. `STW *B15--[n]`), not
from an actual overflow reproduced on the pedal or in simulation.
Commit: this finding.

### S3.F6 - No cycle/deadline check exists in the audio Swi's own call order;
### the only over-budget safety net is the EDMA ping-pong "pick the inactive
### half" address compare, which is a race, not a fault (confirmed call
### order from recon/map/chunk_19.md; likely consequence from recon/16 C4)
recon/map/chunk_19.md's `11818ba0` row gives the **complete, address-level
call order** of the audio Swi (pre-loop stage -> 5-slot loop -> post-loop
stage, every `CALLP` target named). I read that full list looking for any
`TSCL`/`TSCH` read-and-compare, counter increment, or branch to an
error/skip path tied to elapsed time, and found none: the only register loaded
from a hardware timer anywhere in this chunk is unrelated to deadline checks
(the timer-accounting read at `11809f40` mentioned in recon/16 C5 is a
separate, far-away function, not in the Swi's call list). There is no
"missed deadline" counter, no skipped-block flag, and no watchdog call in
`11818ba0`'s own body.

The one mechanism the firmware does have, already confirmed in recon/16
section C4 ("Software selects the inactive DMA half; both input slots reach
DSP"), is purely reactive and local to each DMA direction: RX unpack
(`11818b20`) and TX pack (`11818aa0`) each read the *live* EDMA PaRAM
address (`01c0400c` / `01c04024`) at the moment they run and pick whichever
ping/pong half the hardware is **not currently touching**, then process that
half. recon/16 C4 already states the limit of this scheme explicitly: "an
overrun can cause stale/overwritten blocks and does not gain safety from the
address comparison alone." Concretely: if `11818ba0` takes longer than one
block period (16 frames / 44,100 Hz = 362.8 us per 128 B half, matching
recon/map/chunk_19.md's EDMA-half-size arithmetic) between its own RX-unpack
and TX-pack calls, or between one invocation and the next, the EDMA hardware
keeps running on its own clock regardless; the "currently inactive" half the
Swi reads can become the DMA's *active* half before the Swi finishes with it,
and the half the Swi just finished writing can be re-read by the DMA before
being fully consumed next time. There is no address range-lock, no busy
flag beyond the single ping/pong compare, and no interrupt raised for this
condition anywhere in the traced path.
This matches, without contradicting, the project's own black-box observation
in `docs/DSP_RULES.md` Β§4 ("the effect runs every other block and glitches
(DR103)") - a torn/overwritten half surfaces as exactly that kind of
intermittent glitch, not a hard stop. It does **not** by itself explain the
*other* documented symptom ("the screen freezes and only a power cycle
helps (probes)") - that looks like a genuine hang/fault rather than an audio
tear, and nothing in this chunk's call list offers a mechanism for it; that
is squarely a fault-handling question (Q5, job S4's assignment), not
re-derived or guessed here.
Confidence: **confirmed** (the call-order enumeration and the C4 quote are
pre-existing, cross-checked findings); **likely** for the specific
"over-budget -> ping-pong race -> audible glitch" causal chain (argued from
timing/architecture, not reproduced on hardware or in simulation this
session).
Commit: this finding.

### S3.F7 - The shared stereo bus is one fixed pair of buffers handed
### unchanged to every slot in strict order; SH_CH_B_OFFSET matches the
### firmware's own channel-B addressing exactly (confirmed)
`effects/common/sh_params.h` style headers (checked via
`tests/host/cfm_sh_params.h:12-13`) define `SH_FRAMES = 16` and
`SH_CH_B_OFFSET = 16` (floats), i.e. the bus an effect's `ctx[1]` pointer
refers to is one 32-float (128-byte) object: channel A = `eff[0..15]`,
channel B = `eff[16..31]` = `eff + 64 bytes`.

recon/14 (section 4, "Audio buffers") already confirmed, from
`c014ff58..c014ff7a`, that the service/audio context object is a **single,
fixed** structure at `0x11f03b48`, whose word[1] (`ctx[1]`, what every
effect's `SH_AUDIO_FN(instance, ctx)` receives) is set **once**, to
`0x11f037b0`, L1D RAM - not per-slot, not re-pointed between slots. So every
one of the 5 slots is handed the exact same `eff` pointer.
`0x11f037b0 + 0x40 (64 B = 16 floats) = 0x11f037f0`, matching
`SH_CH_B_OFFSET`'s 16-float stride exactly: channel A lives at `11f037b0`,
channel B at `11f037f0`, precisely the two buffers recon/14 section 4 and
recon/map/chunk_19.md's Data section both already name ("two 16-float
buffers, base+64 apart").
The audio Swi's slot loop (`11818ba0`, confirmed in chunk_19) calls the 5
slot callbacks from table `118133e0` **in strict index order 0 -> 1 -> 2 ->
3 -> 4** (`B10` increments, `CMPGT 5,B10,B0` gates the loop exit), with no
buffer copy or swap between iterations - each slot's effect function reads
and writes `eff[0..31]` in place, so slot N always sees exactly what slot
N-1 left in both channel A and channel B.
Confidence: confirmed (every address and the single-fixed-ctx finding are
pre-existing recon/14 results; the SH_CH_B_OFFSET/address-arithmetic match
and the strict slot-order claim are read directly from
recon/map/chunk_19.md's `11818ba0` row, re-checked by me this session).
Commit: this finding.

### S3.F8 - Traced for the first time this session: who actually produces the
### TX-pack's source buffers (11f038b0/11f038f0), and that it preserves
### channel A/B as two fully independent passes all the way to the final
### stereo output and the planned USB tap (confirmed, new disassembly read)
recon/map/chunk_19.md already named `11f038b0`/`11f038f0` as "planar int
sources for the TX pack, read by 11818aa0" but left their *producer*
unresolved (its own Data section: "sources ... read by 11818aa0" with no
writer cited). I traced it by disassembling `118186e0` (`audio_filter_
stage_b`, listed in chunk_19 as running right before TX pack in the Swi's
post-loop stage) in full:

```text
118186f8  MVK.S1 0x3730,A8 / MVKH 0x11f00000,A8     ; pass-1 source = 11f03730 (channel-A int, from the clamp stage below)
11818702  [A0] SPLOOPD 6                             ; 2-pass outer loop (A0: 2,1 -> 0)
1181877c  SMPY32.M2X   B17,A3,B4                      ; coefficient (c011ad60/11f03e38) x sample
11818798  MVK.S2 0x38b0,B21 / MVKH 0x11f00000,B21    ; dest base = 11f038b0
118187ae  MV.S2 B21,B9
118187b4  STW.D2T2 B4,*B9++[1]                        ; pass-1 store into 11f038b0
118187d8  ADDK.S1 64,A8                                ; pass-2 source advances to 11f037f0-derived 11f03770
11818818  ADDK.S2 64,B21                               ; pass-2 dest advances to 11f038f0
11818820  MV.S2 B21,B9                                 ; (loop back to 118187b8 for pass 2)
11818824  BNOP.S2 B3,5
```
So `118186e0` reads `11f03730` (pass 1) / `11f03770` (pass 2, same +64 B
offset convention as everywhere else in this chunk) and writes
`11f038b0` (pass 1) / `11f038f0` (pass 2). Those int buffers
(`11f03730`/`11f03770`) are, per chunk_19's already-confirmed `11818428`
row, the **channel-A/channel-B float bus clamped to [-1,1] and rescaled to
int32** (pass 1 reads `11f037b0`=channel A, pass 2 reads `11f037f0`=channel
B, same 64-byte-pair convention). Crucially, the SMPY32/SADD math inside each
pass of `118186e0` only ever touches that pass's own registers (B4/B17/A3 for
pass 1; the loop reuses the same registers with advanced base pointers for
pass 2) - **no instruction in this function reads a pass-1 value while
computing a pass-2 result or vice versa**. So channel A and channel B stay
two fully independent signal paths from the bus (`11f037b0`/`11f037f0`)
through the clamp (`11818428`) and this filter tap (`118186e0`) into the TX
sources (`11f038b0`/`11f038f0`), and from there `11818aa0` (TX pack, already
confirmed) scales both and interleaves them with `STNDW` (two 32-bit
words/frame = one word per channel) into the final output ping-pong
`11f03630`/`11f036b0` - the exact ring recon/21_usb_audio_needs.md Β§S1
identifies as **the planned USB-audio tap point** ("Best tap point for a USB
ring copy: right after CALLP 0x11818aa0 ... before the next call", or
alternatively right inside `11818aa0` after its own `STNDW`).
Confidence: **confirmed** (full disassembly of `118186e0` read this session,
addresses and operands quoted above; the clamp-stage and TX-pack ends were
already confirmed in chunk_19/recon/16/21 and are unchanged here).
Commit: this finding.

## Answers

### Q4 - Stack
**Where/how large, and what does overflow corrupt?**
The stack an effect's process callback runs on is the firmware's single
shared L2 Hwi/Swi stack, `0x118134a8..0x11816468` (12,288 B, confirmed
region), reused for every interrupt and every Swi including the audio Swi
(S3.F1, likely). An on-pedal probe (recon/14) saw `B15 = 0x11816140` inside
an effect, i.e. ~808 B of that 12 KiB already spent by the time the Swi calls
down into a slot, leaving on the order of 11 KiB of nominal room below that
point - far more than the project's self-chosen 1536 B per-effect guideline
(S3.F2, confirmed: that number is not a firmware limit, it is a margin set
above DR103's measured 1428 B). Neither `check_slot_mem.py` nor any other
build tool checks an effect's real stack depth; RA200X's `allow_stack: true`
is unenforced documentation (S3.F3, confirmed).
Immediately below the stack's low end (`0x118134a8`) sit, in order: the
live 5-slot effect-callback table (`118133e0`) and second per-slot table
(`11813490`), then the McASP/I2C/EDMA/SPI/sample-rate/clock peripheral-pointer
block (`0x1181329c..0x118134a4`) (S3.F4, confirmed addresses / likely
consequence). An overflow deep enough to reach that low boundary would most
likely first corrupt the very table the Swi uses to find each slot's effect
function - a plausible mechanism for "a bad effect takes down more than
itself" - though this was not reproduced, only argued from address adjacency.
Stock SYS/BIOS stack-overflow error strings (`E_stackOverflow`,
`E_spOutOfBounds`) are linked into the image, but no call site referencing
them was found in the disassembled code (S3.F5, confirmed strings / not
found call site) - consistent with, but not proof of, the checks being
compiled-in but inactive, which would explain silent overflows.
**Can a firmware patch change it?** Not analyzed this session beyond the
above; the stack-size constant (`0x3000` at `c0163e94..3eb4`) is a patchable
data value in principle (same style of patch as recon/16 C10's L2CFG change),
but growing it would need a certified-free adjacent L2 range (recon/16's own
C7/C9 analysis says the known-free L2 tail is only ~24 KB and is earmarked
for slot-heap relocation experiments, not evaluated here against a stack-size
change) - left as a lead, not a plan.

### Q6 - Load and overflow (cycle budget)
**What happens when a block exceeds its cycle budget?**
No check, counter, or skipped-block flag exists in the audio Swi's own
call order (S3.F6, confirmed from the complete call-order enumeration in
recon/map/chunk_19.md). The only budget-adjacent mechanism is the EDMA
ping-pong "read whichever half the DMA is not currently touching" address
compare in RX unpack (`11818b20`) and TX pack (`11818aa0`) (pre-existing,
confirmed in recon/16 C4) - and that comparison is a snapshot taken once per
call, not a lock: if the Swi runs long, the DMA (which runs on its own,
independent clock) can move past the snapshotted state before the Swi
finishes, producing a torn/overwritten half with no warning, no fault, and no
dropped-block accounting anywhere in the traced code (S3.F6, likely as the
specific causal chain). This fits the project's own black-box symptom "the
effect runs every other block and glitches" (DSP_RULES.md Β§4, DR103). It does
not explain the *other* documented symptom (screen freeze on probes) - that
looks like a separate, genuine fault path, which is Q5/job S4's territory and
is not guessed at here.
**Can USB audio survive it?** Not directly tested; since the planned USB tap
reads the exact same final stereo ring that is already subject to this same
race (S3.F8), a late block would hand the USB tap the same torn/stale data
the codec DAC gets - no worse, no better. No evidence of a path by which an
audio-side cycle overrun alone (as opposed to a crashing effect, Q5) would
take down the USB *driver* itself.
**Can a firmware patch change it?** A genuine deadline check (e.g. reading
TSCL at Swi entry/exit and comparing against the known block period, falling
back to silence or holding the previous block instead of processing a
possibly-torn half) is plausible to add at the two existing tap points
(`11818b20` entry, `11818aa0` exit) without touching the DMA setup itself,
but this is a new design, not a located existing hook - risk and patch plan
not worked out this session.

### Q8 - Stereo bus
**How does channel B pass slot to slot, and is a mid-chain stereo write
safe?**
The bus is one fixed pair of buffers (`11f037b0` = channel A, `11f037f0` =
channel B, exactly `SH_CH_B_OFFSET` apart) handed unchanged to all 5 slots;
the Swi's slot loop calls slots 0->1->2->3->4 in strict order with no copy or
reset between them, so each slot reads and writes in place over whatever the
previous slot left in both channels (S3.F7, confirmed). After the slot loop,
channel A and channel B are clamped/rescaled to int32 and filtered by two
genuinely separate per-channel passes (`11818428` then `118186e0`, newly
traced this session, S3.F8 confirmed) with no cross-channel mixing found
anywhere in that path, then packed by `11818aa0` into the final stereo
output ring (`11f03630`/`11f036b0`, two words/frame, one per channel) - which
is the exact ring recon/21 already names as the intended USB-audio tap point.
So: **yes, later slots do read whatever a mid-chain effect wrote to channel
B** (there is only one buffer; every slot sees it), **and the currently
planned USB tap reads a signal path that keeps channel B intact all the way
to the DMA ring** (S3.F7 + S3.F8, confirmed). Mechanically, the bus-passing
and post-loop filter/pack path treats A and B symmetrically and independently
- nothing here mixes, discards, or assumes channel B equals channel A. This
only certifies the *plumbing* is safe for a genuinely divergent stereo
signal; it says nothing about why RA200X specifically crashes the USB driver
when more effects follow it (stack usage, the slot work-buffer
`instance[3]`, or something else entirely) - that causal question belongs to
