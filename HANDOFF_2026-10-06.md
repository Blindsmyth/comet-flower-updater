## 3. The brick and the recovery (read before any pedal write)

1. On 2026-10-05 a `pedal_g1.py replace` of the 56 KB `DR103.ZD2` stalled:
   - all data was sent and the file close (`60 21`) was acknowledged;
   - the pedal then never answered `60 09`;
   - the tool hung in the USB driver and had to be killed.
2. After that the pedal hung at the ZOOM logo on every start.
3. **Zoom's updater v2.00 did not help, and neither did a factory reset.**
   The updater's 8-stage table only writes the boot program, graphics and
   presets, main firmware and settings. It **never writes the effect file
   system**, although it carries a factory image of it (resource 136).
4. **Fix:** `tools/make_fs_restore_updater.py` patches a copy of the updater
   so it erases flash 0x102000 (size 0x2FE000) and writes the factory image
   there. The owner ran it from update mode, and the pedal booted. Full
   procedure: `docs/RECOVERY_G1.md`.
5. **Likely cause (unproven):** the directory has only 127 slots, and the
   factory image already uses 105. A deleted file keeps its slot until the
   firmware compacts the directory. Our wipe of 86 stock effects plus about
   a dozen installs and replaces probably filled it. The DR103 replace may
   then have forced a compaction that hung halfway.

## 4. Flash and file-system facts

**Flash map** (updater table + firmware region table):

| Region | Range |
|---|---|
| Boot program (update mode lives here; **never write**) | 0x000000–0x028000 |
| Factory presets + start-up screen | 0x028000–0x033000 |
| Main firmware | 0x033000–0x0BF000 |
| Settings | 0x0BF000 (4 KB) |
| (Patches?) | 0x0C0000–0x102000 |
| **Effect file system** | 0x102000–0x400000 |

**Updater resources** (in `build/fw/`, extracted from the updater):

| ID | Contents | File |
|---|---|---|
| 129 | main firmware | `res1_493412.bin` |
| 133 | presets + start-up screen | `res2_45056.bin` |
| 136 | factory file-system image | `res3_3137536.bin` |
| 139 | settings (blank) | |
| 142 | boot program | `res5_163840.bin` |

**Stage table:** `.rdata` VA 0x43AC88, 8 entries `[op, addr, size, resource]`;
op 1 = erase, op 2 = write, anything else = skip.

**Effect file system** (`tools/g1fs.py` docstring has the full details):
- 766 blocks of 4 KB; block 0 is the header.
- 4 directory copies (blocks 3/5/7/9): `<seq> A5 <u16 cursor> <live FF/00>
  FF FF FF`, then 32-byte slots up to the first empty one: `<u16 first> 01
  <state FF valid / 00 deleted> <u32 size> <name[12]> FF*12`.
- The cursor is the last data block allocated; the file system writes
  forward from cursor + 1.
- Data block i lives at physical block i + 10: `<prev> <next> <used>` + up
  to 4090 bytes of payload.
- At boot the firmware scans every file (`f_findfirst "*.*"`).
- `BYPASS.ZD2` is not a file.
- Factory image: 105 files = 78 effects + 24 rhythm `.raw` samples +
  `GUARDZDL.ZT2` + `G_OUT_EQ.BDL` + `FLST_SEQ.ZT2`.

**Start-up screen:**
- The first 512 bytes of resource 133 (presets region 0x28000).
- 128×32, LCD page format (4 pages × 128 columns, LSB = top row).
- The firmware draws "v2.0" over the lower part, so keep text in the top
  ~20 rows.

**Factory presets:** 50 `PTCF` records at stride 736 from offset 0x200 of
resource 133. It's a 5-slot variant of the patch format, so it can't be
blanked with our patch tool's format yet.

## 7. Safety rules (updated)

- **Install by update-mode image** (`make_g1_image.py`). It's a whole,
  verified image, and a bad one is undone with the factory restore.
- **Avoid MIDI file writes** (`pedal_g1.py install/replace`) until the brick
  cause is understood. If they're used anyway: one write per session, reboot
  between, and never kill a transfer.
- **Never write the boot program region** (0x0–0x28000).
- AUTO SAVE off; never save a patch with an untested or unmeasured effect.
- **CPU limits:**
  - The UI freezes at about 96–102k cycles/block, and only a power cycle
    recovers it.
  - A kernel over budget causes **audio glitches** (DR103: called only
    every second block).
  - Design to ≤ 80k per patch.
- **Static cycle estimates:**
  - They are trustworthy only for software-pipelined code (808X: 74.5k
    estimated vs ~74k measured).
  - Branchy code can be 3–4× worse (first DR103: estimated 50–70k,
    measured 224k).
- **Build limits:**
  - stack frame ≤ ~1536 B (stock maximum);
  - `.text` < 30 KB link region;
  - no `CALL` in the kernel;
  - no `switch` (it emits a `.switch` section);
  - use `restrict` on block buffers.
- Commits are automatic. Push only when the owner asks.
